# EFFICIENT EXECUTION RULES

目的: Astra / 高推論Sol / Codex Code Mode等の高能力実行で、品質を落とさず、不要なモデル往復・ツール往復・巨大コンテキスト取込・過剰設計・不要なGUI操作を減らす。

## 0. 最優先原則

1. **節約ルールは品質ゲートを上書きしない。** `CURRENT_STATE.md`、現行Issue、Stage Gate、acceptance criteria、protected data safety、回帰テスト、監査条件、再現性・追跡可能性を弱めてはならない。
2. 調査量は減らしてよいが、**完了判定に必要な証拠は減らさない**。
3. 取得失敗した証拠を「たぶん問題ない」で補完しない。必須証拠が取れなければ `BLOCKED` / 未確定として止める。
4. この文書と他の正本が衝突した場合は、より厳しい品質・安全・Stage Gate側を優先し、衝突を報告する。

## 1. Code Modeの並列ツール実行

### 並列化してよいもの

同一の限定された調査段階にあり、互いに独立・非競合・読み取り専用で、結果Aによって結果Bの対象や条件が変わらない呼び出しは、可能な限り1回のCode Mode `exec`セルへまとめる。

例:
- 限定済みの複数ファイル読取
- branch / HEAD / metadata等の独立確認
- 既に対象が確定している複数検索

Code ModeでPromiseを使える場合:
- 一部失敗後も他結果を独立利用できる: `await Promise.allSettled([...])`
- 1件でも失敗したら段階全体を中止すべき: `await Promise.all([...])`

### 並列化前の必須分類

各呼び出しを先に次の2種へ分ける。

- **必須証拠**: 失敗したら完了・PASS・正常・次Gate移行を判定してはいけない。
- **補助証拠**: 失敗しても他の十分な証拠があれば限定的に続行できる。

`allSettled`で多数が成功していても、失敗した1件が必須証拠なら判定を停止する。

### 直列にするもの

次は並列化しない。
- 先行結果で次の検索・対象・条件が変わる適応的調査
- 依存関係のある処理
- 承認が必要な操作
- 待機と再開
- 書き込み
- 競合・相互依存する変更
- 最終検証

### 出力制御

並列実行前に対象範囲、行数、項目数、合計出力上限を絞る。必要証拠が切り捨てられる規模なら意味のある限定段階に分ける。並列化できることだけを理由に調査範囲や呼び出し数を増やさない。

限定段階内で決定的に可能な絞り込み、重複除去、結合、集計、検証は`exec`内で行い、モデルへは最終判断に必要な小さい構造化結果と根拠だけ返す。

## 2. 単純な確認タスクの使用量予算

### 適用対象

次のような**単一値・低リスク・意味が一意な確認**に限定する。
- 現在時刻・期限
- Git HEAD / branch
- working treeのclean / dirty
- 単一Issueのopen / closed
- 単一設定値・単一アカウント状態

原則:
1. ユーザー提示URL、コマンド、画面、GitHub API等の最も直接的な一次情報を1経路だけ確認する。
2. 根拠が得られたら停止する。
3. 回答に現在値として載せるものは、その回答直前の現turnで再取得する。
4. 取得失敗または明確な矛盾がある時だけ代替経路を1つ使う。
5. 外側のモデル・ツール往復は原則2サイクル以内。解決しなければ未確定点と追加調査案を報告して停止する。
6. 単純確認だけを理由にモデル切替調査・サブエージェント生成・全体監査へ拡大しない。

### 適用禁止

次は単純確認として扱わない。
- 「完了したか」
- 「PASSか」
- 「正常か」
- 「次Stage / 次Gateへ進んでよいか」
- 「監査渡し可能か」
- 「本番投入可能か」

これらは通常、複数条件の整合判定であるため、Issue stateだけ、HEADだけ等の1値で決めない。`CURRENT_STATE.md`、現行Issue完了条件、remote branch/commit、必要test、protected確認、report、AUDIT条件等、当該Gateが要求する証拠を確認する。

高リスク、高精度、網羅監査、protected integrity、回帰影響の検証をユーザーまたは正本が要求する場合もこの予算上限を適用しない。

## 3. 小規模修正のスコープゲート

### Planを省略できる条件

仕様、期待挙動、原因、修正箇所が明確な低リスク小規模修正では、Plan Modeを必須にしない。着手前に短く次を固定する。

- 対象
- 最小差分
- 行わない周辺変更
- 実行する検証

ただし、**症状が局所的でも原因が局所的とは限らない**。着手前に、原因も同じ責務境界内へ限定できることを最低限確認する。

### 実装前に簡潔な計画が必要な条件

- 原因または期待挙動が曖昧
- 複数モジュール、公開API、永続化形式、外部契約、主要責務境界へ及ぶ
- 並行処理、再開処理、認証、課金、移行、プロトコルを扱う
- 設計選択肢が複数ある

実際のPlan Mode自体は、ユーザーまたは開発側で選択されている場合だけ従う。変更ファイル数だけで要否を決めない。結果を大きく変える設計選択が残る場合だけユーザー判断を求める。

### 過剰抽象化の防止

将来再利用だけを理由に、新しい共通ヘルパー、抽象クラス、汎用インターフェース、ラッパー、アダプター、レジストリ、設定駆動化、プラグイン機構を導入しない。

API、UI、会話、ワークフロー等の外部形を新規共通化する場合、既存標準・確定契約・明示プロジェクト規約がなければ、独立した実例が原則3件集まるまで固定しない。N=1 / N=2では直接実装を優先する。N=3は判断材料であり、自動的な共通化条件ではない。

### N=3を機械適用しない領域

次はN=2以下でも、安全性・整合性・責務分離のために共有化または一元化が妥当になり得る。
- security / auth
- input validation
- transaction
- protected data integrity
- normalization等の一貫性保証
- external boundary
- 副作用隔離
- 重複による不整合防止

### スコープ超過停止

実装中に、公開契約、新しい汎用抽象化、データ形式・プロトコル、責務配置、依頼と無関係な不具合修正について、依頼または承認済み計画を超える変更が必要と判明した場合は停止し、理由・影響範囲・選択肢を報告する。

同じ目的・責務境界内の局所的なコード、テスト、設定調整は最小差分で続行してよい。

review bot / static analysisの指摘は、現行コードと再現手順で個別検証し、`妥当 / 無効 / スコープ外` に分類する。確認済みのスコープ内問題だけ修正し、一括適用しない。

## 4. GUI実機受入

GUI検証の順序:
1. unit test
2. framework標準GUI test
3. state / coordinate / signal / property等の決定的検証
4. それらでは確認できない範囲だけ実機GUI / computer-use

実機GUIを使う対象:
- 実描画
- OS統合
- DPI / scaling
- focus
- native UI
- 実画面操作でのみ再現する不具合

既存の決定的テストで確認できる範囲をcomputer-useで重複確認しない。

ただし、**ユーザーに見えるレイアウト、DPI、OS統合、focus、native UIを変更した場合は、最終代表ケースの実機受入を省略しない**。自動テストだけで実描画品質PASSとはしない。

GUI plugin / 長寿命sessionの実機受入では、再起動後にバックエンドの公開契約を再取得し、新規の空document / workflow / sessionへ新しく作成した対象を基準に確認する。再起動前から残るtab、対象、DOM、保存状態は古いschemaやscriptを保持し得るため、現行実装の証拠にしない。

## 5. 判定の最終ルール

使用量削減のために省略してよいのは、**重複した調査・重複した推論・不要な抽象化・不要なGUI再確認**である。

省略してはいけないもの:
- 現行task contract確認
- 完了条件
- Stage Gate
- protected data safety / integrity
- 変更影響に必要な回帰テスト
- user-visible GUI変更時の必要な最終実機受入
- provenance / reproducibility / actual Prompt等、正本が要求する追跡証拠
- AUDITが要求する独立証拠

迷った場合は「節約のために品質証拠を減らす」のではなく、調査対象を限定して必要証拠を取り切る。
