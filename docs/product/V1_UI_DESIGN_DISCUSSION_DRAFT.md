## 1. 現時点でかなり強い方向性

DanbooruTagTool は「自動でPromptを完成させるAI」よりも、
**Danbooru系タグを日本語で理解・発見し、自分で選び、最終的に英語Promptとして扱えるローカル辞書兼作業ツール**を目指す。

中心体験候補:

`見る / 読む -> 掘る / 探す -> 選ぶ -> Promptを整理する -> 英語でコピー`

特に、検索語を知らない初心者が「どんなタグがあるのか」を辞書のように眺め、ジャンルや関連概念から掘っていけることを重視する。

## 2. 辞書・検索側の暫定方針

### 辞書を検索しなくても一覧で見られる

- 日本語検索だけに依存しない。
- 辞書をそのまま開き、ジャンル別の一覧を眺められる。
- 一覧からそのままPromptへ追加できる。
- 日本語 / 英語 / 混合検索は同じ辞書探索に重なる補助手段とする。

### Special のジャンル分類を主な探索資産として活用する

完成済み #56 taxonomy を「棚」として使う。

例:

`ジャンル -> サブジャンル -> 該当Special一覧`

さらに、個々の概念から「関連・派生」を掘る体験を重視する。

例:

`ある概念 -> 関連行為 / 組み合わせ / 道具 / 状態 / 構図など`

重要:
- #56のジャンル階層と「関連・派生」グラフは別物として扱う。
- 関連・派生の根拠（manual relation / semantic / co-occurrence / lexical等）は未確定。今後設計する。
- 関連候補を勝手にPromptへ追加しない。

### General 30,629

- #64 が分類を継続する。
- #66 は #64 の分類を独自に作り直さない。
- #64完了後、Generalも辞書一覧・ジャンル探索から使えるようにする。
- #64未完了でもアプリの基本操作は成立する設計にする。

## 3. 表示は Japanese-first、出力は English

### 辞書表示

通常一覧はできるだけ静かにする。

基本表示候補:
- 日本語名
- canonical English tag
- 選択 / 追加操作

常時表示しない方向:
- `Special` / `General` の大きなbadge
- `登録済み` / `未登録` badge
- 重複警告badge
- 内部IDや監査状態などの開発情報

内部では必要なメタデータを保持してよいが、通常UIへ全部露出しない。

### 関連タグ

- 関連候補の見た目は日本語優先。
- canonical English は詳細表示や確認時に追跡できるようにする。
- 日本語と英語を常時すべて二重表示して画面を騒がしくしない。

### Prompt貼り付け時

既存Promptを貼ると、認識できたタグは日本語と英語を対応付けて理解できるようにする。

辞書にない要素:
- 消さない
- 勝手に推測置換しない
- raw textとして保持する
- 日本語訳がない場合は英語/raw表面だけでもよい

### コピー

UI上で日本語表示していても、通常の最終コピーは **英語Promptのみ**。
日本語は理解・確認のための表示層とする。

## 4. 現在の第一候補: 辞書画面 + Prompt編集画面の2画面

2画面は完全に別アプリ化せず、ワンクリックで切り替えられる同一アプリ内の2ワークスペースとする。

### A. 辞書 / 検索画面

主目的:
- 既存Promptを貼り付けて読み込む
- タグを眺める
- 日本語 / 英語で検索する
- ジャンルから発見する
- 詳細・関連・派生を見る
- Promptへ追加する

#### 現在のPrompt欄

右側に **縦長の「現在のPrompt」領域**を置く。

- デフォルト表示は日本語。
- 必要なら `日本語 / 日本語+英語 / 英語` を切替可能にする候補。
- 数十タグをなるべくスクロールせず一覧できるよう、右欄を下まで広く使う。
- `Prompt編集を開く` と `英語Promptをコピー` を置く。
- 辞書画面では誤操作防止のため、現在Prompt内の各タグに削除用 `×` を常設しない。
- `最近追加` の専用パネルは置かない。現在Prompt表示に空間を優先する。
- 辞書画面で本格的な並べ替え・大量削除はしない。

#### 既存Prompt貼り付け

上部の `既存Promptを貼り付け` は保持する。

これは重要な入口であり、削らない。

`英語Promptを貼る -> 認識可能なタグを日本語表示 -> 辞書探索 / 追加 -> 必要ならPrompt編集`

という流れを想定する。

### B. Prompt編集画面

**編集に特化する。辞書情報を再表示する画面にはしない。**

主目的:
- 数十タグを一気に見渡す
- ドラッグ&ドロップで並べ替える
- 不要タグを削除する
- 最終英語Promptをコピーする

現時点の強い候補:
- フラットで高密度な日本語タグカード / チップ表示
- 30〜80タグを扱っても一覧性を落としすぎない
- ドラッグ&ドロップで直接順序変更
- 削除はPrompt編集画面で行う
- 英語タグ列を常設しない
- `操作` 列を設けない
- `役割 / カテゴリ / Special / General` などのbadgeを各タグへ常時付けない
- ジャンルごとの大きな箱分けをしない
- 分類や意味を確認したい場合は辞書画面へ戻る

右側には:
- `現在のPrompt（日本語）`
- `英語Prompt（コピー用）`
- `英語Promptをコピー`

程度を置く候補。

Prompt編集画面では「分類を見る」より「編集速度・一覧性」を優先する。

## 5. 未解決タグの扱い

未解決タグの大きな専用パネルは **置かない**。
画面スペースを消費しすぎるため不採用方向。

代わりに:
- raw token自体はPrompt内で保持する
- 小さな `未解決を登録 (N)` のような入口だけ置く候補
- ユーザーが登録した未解決語を別ファイル / review queue に蓄積する
- たまにまとめて調査・日本語辞書へ反映する
- 未解決だからといって自動削除・自動分類・推測置換しない

review queueの具体的なファイル形式 / path は未確定。
UIから独立した小さなデータ資産として扱う。

## 6. 実Prompt長を前提にする

短いUI mockupの5〜8タグだけを基準にしない。

Noob / WAI系の通常運用では、外見・衣装・ポーズ・構図・背景・style等を含めると数十タグになることを前提にする。

UI設計上は少なくとも:
- 30〜60タグ程度を普通に扱える
- 50〜80タグでも破綻しない
- 1画面でできるだけ多くのタグを見渡せる
- 日本語+英語の2段常時表示で縦方向を無駄にしない

ことを重視する。

## 7. 画像スペースは置かない

通常アプリは画像生成・画像プレビュー自体を主機能にしない。
UI mockupで使った画像サムネイル領域は実運用では不要。

その空間は:
- 辞書一覧
- 日本語説明
- 関連 / 派生
- 現在Prompt確認

に使う。

## 8. 技術構成の第一候補

作り直す場合の第一候補:

- C#
- .NET / WPF
- SQLite
- CommunityToolkit.Mvvm 等の軽量MVVM補助

想定:
- Windowsローカル専用
- 非LLM runtime
- 画像生成ソフトと同時利用しても軽量
- UIとデータアクセスを分離

依存方向の候補:

`WPF View -> ViewModel -> Application Service -> Repository / SQLite`

UIから直接SQLやcanonical変換ルールを持たせない。

## 9. 将来の辞書追加を前提にしたデータ構造

Special / General をコードへ固定的に埋め込まない。

原則:

> **新しい知識は、可能な限りコード追加ではなくデータ追加で導入できること。**

辞書を共通の **Data Pack** として扱う案を第一候補にする。

概念例:

```text
DataPacks/
  special-core/
    manifest.json
    tags.csv
    japanese.csv
    aliases.csv
    categories.csv
    relations.csv

  general-ja/
    manifest.json
    tags.csv
    japanese.csv
    categories.csv

  future-dictionary/
    manifest.json
    ...
```

実行用SQLiteは:

```text
GitHub上の正本 CSV/JSON/sidecars
        ↓
     Data Packs
        ↓
  Import / Validate
        ↓
     catalog.db
        ↓
      WPF app
```

を想定。

### catalog.db と user.db を分離

候補:
- `catalog.db` — Special / General / 日本語 / Alias / taxonomy / relation等。再生成可能。
- `user.db` — お気に入り / 履歴 / 保存Prompt / 個人設定等。

これにより辞書更新時にcatalogを作り直してもユーザーデータを守れる。

数万件規模では高度な差分アップデータを最初から作らず、必要ならcatalog.db全再構築でもよい。

## 10. Noob / WAI17への考え方

想定利用モデルとして NoobAI / WAI Illustrious 系を意識するが、辞書探索そのものをモデルごとに分断しない方向。

共通コア:
- 日本語で理解
- タグを発見
- 自分で選択
- canonical Englishで出力

モデル別の推奨順序・品質タグ・有効性ヒント等は、必要性が確認できてから別レイヤーで扱う。
v1の基本探索UIをモデル固有知識で複雑化しない。

## 11. UIの見た目に関する暫定原則

- 表側はシンプル、裏側はリッチ
- 常時見える情報を増やしすぎない
- 日本語を主にして英語は追跡可能にする
- 「今何をする画面か」が一目で分かる
- 管理画面・監査ツールのような見た目にしない
- Prompt編集画面は編集効率を最優先する
- 辞書画面は理解・探索を最優先する
- 画像生成ソフトと同時起動しやすい軽量なWindowsデスクトップアプリを維持する

## 14. 最新の短縮版 / チャット引継ぎ

> **辞書画面**は「既存Promptを貼る / 辞書を一覧・検索・ジャンル探索する / 詳細や関連を見る / タグを追加する」場所。右側には日本語中心の現在Promptを縦長に広く表示し、ここでは誤削除を避けるため削除×を置かない。
>
> **Prompt編集画面**は「数十タグを高速に編集する」ことだけに特化。ジャンル箱・役割badge・英語列・操作列は置かず、日本語タグを高密度に並べ、ドラッグ&ドロップで順序変更し、削除もここで行う。意味や分類を見たければ辞書へ戻る。
>
> **未解決タグ**は大きなUIを占有せず、小さな「未解決を登録」入口から別review queueへ蓄積し、後日まとめて辞書へ反映する。
>
> **技術候補**は C# + WPF + SQLite。辞書はData Pack化し、Special追加・General更新・将来の別辞書追加をアプリ本体の改造なしで行いやすくする。catalog.dbとuser.dbは分離候補。
>
> **この内容は次の設計検討の開始地点であり、まだ最終仕様ではない。**
